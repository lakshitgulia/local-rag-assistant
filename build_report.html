01

What this is

The client wants scattered PDFs, policies, reports and emails turned into one assistant that answers instantly and shows the exact passage behind every answer. This POC proves the mechanism end-to-end on real files pulled from this machine — not synthetic sample data — using a fully local stack: LangChain's hybrid retrieval (FAISS + BM25, reciprocal rank fusion) and Ollama for both embeddings and generation. Six real bugs surfaced across the original build and two follow-up rounds (a model-speed switch and a LangChain migration) and were fixed in place; all are documented below with root cause, not just the patch — see Sections 5, 10, and 11. A real measured accuracy number — 13/15 (87%) — is in Section 12.

Kept deliberately small: LangChain's own Embeddings/VectorStore/LLM base classes are the swappable-provider interface, so a provider swap later touches core.py's two getter functions, not the pipeline. The email connector from the original build was removed entirely in the LangChain migration (Section 11) — not listed here because it no longer exists in the project.

How hybrid retrieval actually decides a citation

05

Two real bugs, found by actually running it

Bug 1 · ingestion crash ingest.py
Symptom
Ingestion died mid-run: requests.exceptions.HTTPError: 500 from Ollama's /api/embeddings.
Root cause
Chunking split text by word count (600 words/chunk). One PDF's text extraction glued glyphs together with no spaces, so one "word" alone was long enough that its chunk tokenized to 4,638 tokens — past Ollama's 2,048-token batch limit. Confirmed in ~/.ollama/logs/server.log: input (4638 tokens) is too large to process.
Fix
Switched chunking to character-based slicing (2,000 chars, 13% overlap) — bounded regardless of whitespace, immune to run-on extraction artifacts. Verified: full re-ingestion completed clean, 882 chunks.
Bug 2 · silent retrieval degradation core.py
Symptom
Short questions like "What is AutoMind?" returned the no-answer fallback even though a 0.777-similarity match existed — the LLM saw irrelevant noise and gave up.
Root cause
BM25 tokenized with plain .split() — no punctuation stripped. The query token "automind?" never matched the corpus token "automind", so BM25 scored almost entirely on stopwords ("what", "is") and surfaced an unrelated ML paper's diagram text and OS lecture notes instead.
Fix
Added a regex tokenizer ([a-z0-9]+) used consistently at index-build and query time; rebuilt bm25.pkl from the existing chunks. Verified: same question re-tested, now returns a correct grounded answer citing 3 genuinely relevant documents.

Three targeted fixes on top of the working build above — no scope beyond what was asked. Each is reported the same way as the original bugs: root cause, fix, verified before/after.

1

Answers were too short

Root cause
Confirmed by checking in the order requested: the prompt never asked for elaboration (it only said "answer using the excerpts," nothing about depth). num_predict was unset (Ollama's implicit default, not an explicit cap). Context width was already CONTEXT_K = 5 — already in the suggested 3–5 range, not the cause.
Fix
Added an explicit elaboration instruction to PROMPT_TEMPLATE in retrieval.py, and set num_predict: 700 in the Ollama call in core.py.
− (before) no elaboration instruction
+ (after) "Answer thoroughly using the specific details, numbers, and facts present in the sources below. Do not give a one-line summary — explain the relevant details and reasoning a staff member would actually need, drawing on every excerpt that's relevant, not just the first one."

Architecture change

The hand-rolled EmbeddingModel/VectorStore/LLM ABC classes are gone. LangChain's own Embeddings/VectorStore/LLM base classes already are the swappable-provider interface this project needed — wrapping them in a second custom abstraction layer would have been indirection on top of indirection, which every cleanliness audit on this page has been checking against. core.py now just exposes get_embeddings() and get_llm().

EnsembleRetriever vs. hand-written RRF: your instructions said use it only if its fusion algorithm is equivalent to reciprocal rank fusion. Read the actual source (langchain_classic/retrievers/ensemble.py) instead of assuming — it implements weighted RRF with the identical default constant (c=60) the hand-written version used. Verdict: equivalent, so it replaced the hand-written fusion outright.

Why it isn't one unbroken retriever | prompt | llm pipe: the guardrail has to inspect retrieved documents before deciding whether to call the LLM at all, and citation-building needs those same documents after generation. Both are project-specific with no LangChain built-in, per the brief. So retrieval+role-filtering runs as a plain function call, and only the generation half — PROMPT | llm | StrOutputParser() — is an LCEL chain.

The one new bug this migration introduced

Migration bug · ingestion crash ingest.py
Symptom
ollama._types.ResponseError: ... connection reset by peer (status code: 400) after 30.6s, mid-ingestion.
Root cause
OllamaEmbeddings.embed_documents() sends the entire text list in one HTTP request — unlike the old hand-written loop, which embedded one chunk per call. Handing it all 882 chunks at once overwhelmed Ollama's /api/embed endpoint.
Fix
Batch client-side at 64 chunks/call in ingest.py. Not an arbitrary number — it's the exact batch size the DPR document itself specifies as the intended production design ("Embed chunks in batches (64–128 per call)"). Verified: tested on a 3-file/143-chunk subset first, then the full 74-file corpus completed clean — 882 chunks, identical count to pre-migration, zero errors.

Both failures investigated, not just logged

Failure · wrong document entirely cns nida 1-20260314084625.pdf
What happened
Question about security-attack categories retrieved 3 completely unrelated files instead.
Root cause
Checked the actual indexed text for this file: it extracted with zero spaces between words — "UNITI:SecurityConcepts(Part1)...Informationsecurityistheprocessofprotecting...". This breaks BM25 outright (the whole run becomes one unmatched token) and likely degrades the embedding too. A source-file extraction-quality problem — the same category as the very first bug in this project, just silently degrading one file's retrievability instead of crashing ingestion.
Not fixed
Out of scope for this pass per your instruction not to tune after seeing results. Flagging it as a real, named limitation of the current corpus rather than hiding it.
Failure · right document, wrong section DPR_Internal_Knowledge_RAG_Assistant.docx
What happened
Question about the four scope exclusions returned no citation at all.
Root cause
Queried retrieval directly to check: the DPR's opening/title chunk got retrieved, not the chunk further into the document that actually lists the exclusions. Confirmed by string-checking the retrieved chunk's content — it does not contain the exclusion list. The model correctly declined rather than guess; it simply didn't have the right chunk in front of it. Since DOCX chunks are all labeled generically "document" (no page numbers, unlike PDFs), this is the DOCX-equivalent of a "right doc, wrong page" miss.
Not fixed
Same reasoning — a real, honest limitation of chunk-level retrieval granularity on long DOCX files, not tuned away after the fact.
